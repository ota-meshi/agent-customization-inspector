### Session 2026-07-15

- Q: What establishes the Repository source root? → A: The selected Repository root: the exact process working directory returned by the one `process.cwd()` capture when `--root` is omitted, or the one `--root` value — kept as given when absolute and otherwise resolved lexically against the capture with the active platform's `node:path.resolve`. The initial release has no separate repository picker or ancestor-root discovery.
- Q: Which term should describe the first product scope? → A: Use “initial release” throughout the specification.
- Q: What should the specification call a discovered agent-customization file? → A: Use “customization file” throughout the specification.
- Q: What should the specification call the documented set of filesystem paths eligible for inspection? → A: Use “inspection path allowlist” throughout the specification.
- Q: How must vendor lookup tables and their evidence be organized? → A: Keep vendor lookup behavior separate from Inspector matchers and runtime composition; use separate product documents, separate Repository and User/Global tables, separate GitHub Copilot VS Code/CLI/Cloud tables, and stable official-source references for every maintained row.

### Session 2026-07-16

- Q: What runtime implementation constraint applies to the initial release? → A: Implement all executable application code as JavaScript/TypeScript. The CLI, local host, and inspected-source I/O run on Node.js public JavaScript APIs, while the browser receives generated JavaScript plus declarative HTML/CSS assets; strict JSON manifests, documentation, and license files remain valid package data. Do not use Rust, Node-API or other native addons, prebuilt native binaries, package-lifecycle compilation, or package-lifecycle/runtime artifact downloads.
- Q: What filesystem-race guarantee is possible under that Node.js-only constraint? → A: Centralize inspected-source I/O in one Node.js module, reject links and boundary failures exposed by public Node.js APIs, compare root, ancestor, candidate-path, open-handle, and post-read identity, canonical-location, and metadata snapshots, and discard all candidate bytes when a mismatch is detected. Use `O_NOFOLLOW` as final-component defense in depth when Node.js exposes it and the platform enforces it. The threat model excludes an adversarial local process that races a source root or ancestor or, where effective `O_NOFOLLOW` is unavailable, final path component between these non-atomic checks; public Node.js APIs also cannot reveal every same-device mount or reparse behavior. These residual risks and their Node.js or operating-system resolution paths must remain documented.

- Q: What does it mean for Repository results to remain unchanged when Global enablement commits? → A: The Repository Source keeps its stable `sourceId`, and its customization-file membership, source-relative paths, readable or diagnostic states, recognitions, relationships, Repository-scoped diagnostics, and authored source text remain semantically unchanged because that operation does not rescan the Repository. - Q: What location context does each Diagnostic carry? → A: Every retained Diagnostic has exactly one scope. Scope describes location independently of whether the Diagnostic belongs to a committed generation or the session lifecycle.
- Q: How is SC-008 scored? → A: Maintain semantically equivalent English and Japanese WCAG 2.2 AA applicability matrices that enumerate every Level A and AA success criterion. - Q: Which scan does each SC-002 run measure when the Repository scan starts automatically? → A: Wait for the automatic initial Repository scan to finish, then have the browser submit one explicit Repository rescan. The admission response supplies an opaque `scanRequestId`; qualifying status, the successful commit, and the rendered inventory must all identify that same request. Only the generation committed by that request can stop the 10-second timer, so an earlier automatic inventory or status can never satisfy the run.
- Q: What counts as an inspected-source mutation? → A: Count product-issued requests to write, truncate, create, rename, delete, link, change mode or ownership, set times, extended attributes, or ACLs, or open with mutation-capable flags. The Inspector issues none. A read-side access-time update performed solely by the operating system is outside product control and is not counted as a product-issued mutation; tests record it separately, never request it, and never use it as evidence that the Inspector mutated the source.
- Q: What structural interpretation is allowed without making the Inspector a semantic analyzer? → A: Allow syntax-only parsing, reading the values a parser resolves for the declarations the recognized kind publishes, classification against frozen documented catalogs, and projection of documented order, scope, condition, selection, and reference relationships. Across inventory, detail, comparison, Global controls, diagnostics, API responses, CLI output, and documentation, do not interpret or rank natural-language meaning, decide correctness, effectiveness, compliance, or quality, or provide remediation advice.
- Q: Is sensitive-content acknowledgement an API authorization factor? → A: No. The loopback-only bind of the unauthenticated session host is the access-control boundary. No acknowledgement gate exists (2026-07-28): standing in front of a loopback-only session showing the viewer their own files, it guarded nothing while making every file take two interactions to read. A detail or comparison surface shows the file exactly as written; it neither asks first nor carries a notice about what the content may contain, which would spend the screen telling a reader about their own repository. What survives is the handling: authored content is held in browser memory only, is reachable only by an explicit request for one file or one comparison, and a client-data purge is the central full-session client reset that clears inventory, detail, comparison, editor models, and in-memory metadata after document-liveness failure or an equivalent terminal reset. The Global-disable action MUST perform that purge before sending its request, and observation of a greater Global content epoch or a non-null disable fence MUST repeat it before rendering. Closing a route, ordinary file or Source removal, or changing generation may instead dispose only the affected models and is not by itself a client-data purge.
- Q: Does the Inspector define file-size or item-count validation limits? → A: No. File and collection capacity is determined by Node.js, the parser, the operating system, the filesystem, the browser, and the execution environment. The Inspector does not reject or classify customization content by a product-defined size or count ceiling. A failure confined to one file surfaces as that file's Diagnostic (FR-028); any other thrown exception or rejected operation aborts the affected publication attempt — the file and scan layers never inspect its cause to reclassify, retry, or recover it, and the one closed cause check is the resource-exhaustion errno set (`EMFILE`, `ENFILE`, `ENOMEM`) that routes a read failure to this abort instead of into a per-file outcome; that attempt commits no item, Source, recognition or derived result, scan-result record or success response, or generation, never authorizes a partial generation, and leaves only any prior committed snapshot available.
- Q: When may a scan publish a partial generation? → A: Only after complete traversal and generation assembly when one or more published files produced an FR-028-eligible deterministic, non-throwing entry-local outcome as data while unaffected files remain complete. A published file is an admitted candidate or a file a companion census listed beside one; being listed is not being admitted, but it is read the same way. A failed read counts the same for both. A companion whose bytes are binary is the ordinary published fact of an asset — nothing expected it to be text — so it carries no Diagnostic and makes nothing partial, where an admitted candidate's binary content stays diagnostic-only because a rule admitted that file as a text customization (2026-07-29). Complete outcomes such as readable `utf-8-replaced` text are expressly excluded from that partial condition. A read, decode, parse, or extraction failure at the single-file boundary becomes that file's contracted entry-local outcome (FR-024/FR-028 and the Closed Scan Publication Outcomes table), classified by where the failure occurred rather than by inspecting its cause. A recoverable environment or resource failure is not such a failure even when it surfaces during one file's read: it is a fact about the environment rather than about that file, so calling the file unreadable would report a condition of the machine as a property of the user's content. Any exception or rejected operation outside that single-file boundary — from coordination, assembly, serialization, transport, or lost authority — is never converted into an entry outcome and never authorizes partial publication. A recoverable environment or resource failure aborts the whole publication attempt and publishes nothing (Constitution § Quality and Safety Standards).
- Q: How are read bytes decoded? → A: Any NUL byte classifies the file as binary — for an admitted candidate that classification is diagnostic-only, while a census-listed companion's binary bytes are its ordinary published fact. Otherwise decode once as UTF-8 using replacement semantics, recording and removing one leading BOM when present. When invalid byte sequences are replaced with `U+FFFD`, record `utf-8-replaced` and pass that exact garbled decoded string through display, parsing, extraction, and comparison. Never detect or retry another encoding.
- Q: Does an absolute Global root outside the ordinary home fail merely because of its location? → A: No. An absolute configured root (active-platform `node:path.isAbsolute`) is eligible for post-consent admission even when it is outside the ordinary home. Absence selects the documented default; empty, relative, invalid, or inaccessible roots follow the closed outcomes below and never create fallback authority.
- Q: How are the release-evidence denominators for SC-003, SC-004, SC-005, and SC-007 frozen? → A: A checked-in, versioned release-evidence fixture manifest assigns stable case IDs, required classes, fixture or builder references, expected outcomes, and content digests to those criteria. The manifest version and digest identify the exact denominator used for a release candidate; a missing case, unexecuted case, digest mismatch, or empty required class fails the affected criterion. Removing or reclassifying a case, changing a required-class definition, or changing an expected outcome requires an explicit manifest-version increment and review rather than silently weakening the denominator. A fixture-byte-only change instead requires both the referenced-fixture digest and canonical manifest digest to change. Either kind of change starts a new non-comparable measurement set.

### Session 2026-07-20

- Q: Does generation 0 require filesystem admission before the Repository Source exists? → A: No. Session bootstrap MUST capture the invocation working directory from `process.cwd()`, select the Repository root from that string or a valid `--root` value using lexical path operations only, and create exactly one Repository Source synchronously with zero filesystem I/O. Its escaped root label and stable `sourceId` are non-authorizing session identity only; the first scan simply reads the retained raw selected root — there is no separate admission layer. A deterministic scan failure — including a root that does not exist or cannot be read as a directory — leaves that Source present with failed scan status, retains its source-scoped `root-unreadable` Diagnostic (FR-002), and publishes no customization files or generation. A thrown or rejected automatic-startup operation instead propagates to the process top level and may end the process or session.
- Q: How may a user select a Repository root other than the invocation working directory? → A: The CLI MUST accept `--root <path>`. When omitted, the selected Repository root is the exact string from the one `process.cwd()` capture. An absolute option is kept as given, and a relative option is resolved lexically against the captured invocation directory with the active platform's `node:path.resolve`. A repeated `--root` resolves to the argument parser's last value (deterministic last-wins) and is not separately rejected — repeated-argument policy belongs to the argument parser. An explicit empty value MUST produce a fixed actionable, source-value-free startup error and exit before creating a session or opening a browser. A missing value MUST be rejected at the same boundary by the argument parser's typed validation; the product MUST NOT duplicate that parser-owned check. Root selection itself MUST perform zero filesystem/network I/O, and the rejected launch MUST perform no invocation-`cwd`-, `--root`-, or selected-root-derived I/O and no DNS, SMB, or outbound-network call. The selected root's readability is established only by the first scan, which fails with the source-scoped `root-unreadable` Diagnostic when the root does not exist or cannot be read as a directory.
- Q: Which tools does one Global-inspection consent enable? → A: Consent is session-wide, not tool-selective. Before consent, the product performs no proposed-root filesystem I/O. After one explicit Global opt-in, one transaction MUST attempt all three frozen preview entries and automatically include every root that is structurally present and passes admission. The user cannot select or deselect individual tools. A lexically invalid root, an exact structural `lstat` absence, or a deterministic link/type/boundary rejection creates no Source and does not block the admitted subset; all admitted Sources publish together in one atomic generation. Any thrown or rejected operation not confined to one file aborts that transaction as the failed request's ordinary error and commits none of its subset. If no root is admitted and no operation throws or rejects, the transaction uses the documented all-rejected outcome.
- Q: How are the three Global root inputs captured consistently across platforms? → A: On each request that creates a new unconsented preview, read `COPILOT_HOME`, `CLAUDE_CONFIG_DIR`, and `CODEX_HOME` exactly once each in that fixed order. A value is absent only when the captured value is `undefined`; an empty string is a present override. If any value is absent, call the imported `node:os.homedir()` exactly once for that request and lexically append `.copilot`, `.claude`, or `.codex` with the active platform's `node:path.join` for the corresponding absent value. Do not separately choose among `HOME`, `USERPROFILE`, or another platform variable. This capture performs no filesystem operation or existence check. Any throw/rejection during environment capture, `homedir()`, joining, retention, escaping, or preview serialization fails that invocation with its ordinary real error at the session RPC boundary and creates no preview or authority. A successfully created preview freezes all three exact strings and is never recaptured while active consent uses it.
- Q: How are root strings classified, displayed, and bound without Unicode or escape ambiguity? → A: Assign Global state in order: a present environment string of length zero is `present-empty`; a string containing U+0000 or an unpaired UTF-16 surrogate is `invalid`; otherwise active-platform `node:path.isAbsolute` false is `relative`; and a remaining absolute spelling is `eligible` — the platform's own path handling owns spelling semantics. For every Repository or Global root label, iterate exact UTF-16 code units without normalization: copy only ASCII letters, digits, `.`, `/`, `:`, `_`, and `-`; encode every other code unit as `\uXXXX` with four uppercase hex digits, including each surrogate half and every backslash. Render that ASCII result as text, never HTML, and never decode it for I/O. A preview is the one server-retained record identified by its opaque `previewId`, and what would be read below an admitted root is bound by the digest-free `allowlistVersion`/`traversalPlanVersion` pair; the pair carries no digest because the server never re-verifies its own retained state cryptographically.
- Q: Who handles a runtime file-read error? → A: A failure confined to one file becomes that file's per-file Diagnostic (FR-024/FR-028). Any other rejected Node.js operation is not caught by the file, parser, recognition, or scan layers to classify, retry, or recover; it propagates to the execution boundary that owns the trigger. For a session-API-owned operation, the failed request reports its real error ordinarily — directly if the request has not been accepted, or retained per FR-030 as the terminal error of the already accepted job — and the process and prior committed snapshot stay available. For an automatic startup operation with no request owner, the error propagates to the process top level and the product does not promise process survival. Neither path commits a failed-attempt item, result body, or generation.
- Q: How can expected absence coexist with runtime-owned file-read errors? → A: Only the probe of a contract-declared exact target (the Global exact-file rules, including the Codex override/fallback pair) MAY treat a missing entry (`ENOENT`/`ENOTDIR` from the existence probe) as the closed `absent` outcome. This narrow conversion MUST NOT inspect the message, infer another cause, or apply to any other code or operation. A read failure after discovery — including a broken symbolic link — is that file's `file-unreadable` Diagnostic (FR-024); there is no `entry-disappeared` or race-detection taxonomy.
- Q: What happens to non-NUL bytes that are not valid UTF-8? → A: Process the replacement-decoded garbled text as-is. Decode once with UTF-8 replacement semantics, preserve every resulting `U+FFFD` in `sourceText`, label the encoding `utf-8-replaced`, and continue ordinary parsing, extraction, display, and comparison. This decode outcome is complete rather than partial by itself. Do not guess a source charset or try a second decoder. A NUL-containing admitted candidate remains `binary`, diagnostic-only, and a file-confined `partial` outcome; a census-listed companion's binary bytes are its ordinary published fact.
- Q: How are Unicode-normalization collisions and multiple hard-link paths represented? → A: For an enumerated path, retain the exact raw entry-name segments returned by `Dirent.name`; for a targeted fixed path that intentionally performs no parent enumeration, retain the exact immutable registry target spelling. That provenance-specific spelling is both the filesystem operand and — joined with `/` — the public Source-relative Path used for matching and display: nothing is normalized away, a filesystem holds one entry per name so every published path is unambiguous, and presentation escapes control characters without changing the stored value. ### User Story 1 - Discover Repository Customizations (Priority: P1)

A developer selects the intended Repository root by changing to it or supplying `--root <path>`, launches the inspector through `npx`, and receives a browser-based inventory of the customization files recognized for GitHub Copilot, Claude Code, and OpenAI Codex. **Acceptance Scenarios**:

5. **Given** files outside the repository inspection path allowlist, **When** the repository is scanned, **Then** those files are not interpreted or presented as customization files.
6. **Given** no supported customization files, **When** the scan completes, **Then** the user sees a successful empty state that explains the supported scope rather than an error.

#### Closed Global Root Admission Outcomes

| Configured-root input or phase | Closed outcome |
|---|---|
| Setting absent | Derive the documented default string and classify it through the rows below; no I/O before consent |
| Captured environment setting has length zero | `present-empty`; retain the invalid preview entry without a root, Source, or scan job |
| The string contains U+0000 or an unpaired UTF-16 surrogate | `invalid`; retain no authority |
| Active-platform `node:path.isAbsolute` returns false | `relative`; do not resolve or fall back |
| Otherwise | `eligible`; the exact string is frozen into the preview and carries no read authority until consent |
| Submitted consent does not match the current frozen preview | Reject the request; create no authority, root, Source, or scan job |
| A consented root is missing or is not a readable directory | Record that tool as absent or failed without preventing the other tools from committing |
| One or more consented roots are readable directories | Admit each such root and commit its Global Source in the single atomic batch generation |

#### Byte Decode Outcomes

| Byte condition | Encoding state | Source and comparison outcome |
|---|---|---|
| At least one NUL byte | `binary` | Expose no source text or comparison eligibility. For an admitted candidate this is diagnostic-only and makes an otherwise publishable generation `partial`; for a census-listed companion it is the ordinary fact of an asset, with no Diagnostic |
| No NUL; all bytes are valid UTF-8 | `utf-8` | Record and remove one leading BOM when present; expose the complete decoded source and allow comparison |
| No NUL; one or more invalid UTF-8 byte sequences | `utf-8-replaced` | Decode once with replacement semantics, record and remove one leading BOM when present, preserve the resulting garbled text including every inserted `U+FFFD`, and continue ordinary parsing, extraction, source display, and comparison; do not detect or retry another encoding |

### Edge Cases

- The selected Repository root cannot be read, becomes unavailable after startup, or is not the root the user intended to inspect; the invocation `cwd` itself may also become unavailable before `process.cwd()` can be captured.
- A file at an allowlisted inspection path is a symbolic link (read through its target like any other file; a broken link yields a per-file diagnostic) or disappears between discovery and reading (per-file diagnostic).
- A supported filename contains invalid text encoding, malformed frontmatter or configuration, extremely long lines, or binary content, or the execution environment reports that it cannot continue processing the file.
- One customization file has multiple recognized file types or recognizing tools.
- A customization file references another file through an absolute path, `..` traversal, environment-variable text, or a chain of imports; the reference stays authored text and no target is opened.
- A configured tool home is missing, empty, relative, inaccessible, or outside the user's ordinary home location.
- A Global override file exists but is empty; the documented fallback file may then apply.
- Files change while the browser is open, including sensitive content becoming newly present.
- An explicit rescan fails fatally after producing partial results; the partial results are discarded and the last successfully committed snapshot remains visible with a stale marker and failure diagnostic.
- A browser session is refreshed or opened from a host other than the initiating machine.
- A customization file contains a literal credential or an environment-variable reference whose variable is set in the Inspector process; the literal source is displayed without masking, and the reference is not resolved or substituted.
- A read causes the operating system to update access time even though the Inspector issued no mutation-capable filesystem request; that OS side effect is recorded separately and does not fail the product-issued-mutation assertion.
- An admitted operation fails unexpectedly during I/O, decoding, parsing, assembly, or transport: a file-confined failure becomes that file's diagnostic (FR-028); anything else fails the attempt while the last committed snapshot stays visible and the failure is reported as an ordinary error.

#### Closed Scan Publication Outcomes

| Terminal condition | Public status | Commit and response outcome |
|---|---|---|
| Traversal is complete and every file has a complete result (including readable `utf-8-replaced` results) | `complete` | Atomically commit one complete generation |
| Traversal is complete and one or more files have only file-confined outcomes (unreadable, an admitted candidate's binary content, parse failure — a census-listed companion's binary bytes are its ordinary fact and confine nothing, FR-025) while every unaffected file is complete | `partial` | Atomically commit one generation with affected-file diagnostics and complete unaffected results |
| The attempt fails before commit | `failed` for that `scanRequestId` | Commit nothing from the attempt; report the failure as an ordinary error; retain any prior committed snapshot. If and only if this is an explicit rescan, mark the retained snapshot stale for that Source |
| Disable, shutdown, or supersession revokes publication authority | No later success status | Discard every late result and commit nothing from the revoked request |
| Response transport fails after an atomic commit | Committed status unchanged | The client refetches the committed generation through the session API |

GitHub Copilot is the exception in the other direction: it documents `name` as an optional display name and identifies a profile by its configuration file's own name minus `.md` or `.agent.md`, so a Copilot row is named from the path and a row of its named after the declared `name` would report an agent Copilot does not deduplicate under it. Which fact answers is therefore the admitting rule's, not the kind's, and one file two products recognize defines on two rows whenever their answers differ. A custom-agent row is also the one identity that can be genuinely absent, and only under a declared-`name` product: a file declaring none, one declaring anything but a scalar, and one whose declarations could not be read at all share the single row whose name is null, which is not a name and carries no authored value. A client-data purge MUST be the central full-session client reset that clears inventory, detail, comparison, editor models, and in-memory metadata after document-liveness failure or an equivalent terminal reset. The Global-disable action MUST perform that purge before sending its request, and the client MUST repeat it before rendering after observing a greater `globalContentEpoch` or non-null `globalDisableInProgress`. Route closure, ordinary file or Source removal, and generation change MAY dispose their scoped models without constituting a client-data purge. Nothing in this requirement is an access-control factor: the session API is reachable only through the loopback-bound local host, which is the whole boundary. The initial release MUST NOT provide credential masking or a reveal workflow.
- **FR-028**: A problem confined to one file—an unreadable file, binary content, or a parser or extractor failure—MUST NOT prevent other files from being discovered or viewed. The affected item MUST retain enough source-relative path and Source context for the user to resolve the problem. A parser or extractor failure MUST keep the complete readable source (including any replacement characters) displayed and comparison-eligible while omitting only the affected recognition's derived metadata or relationships.
- **FR-029**: The Inspector MUST NOT define product-specific numeric validation limits for file size, file or item count, parser structure, request or response size, work queues, scan duration, filesystem operations, open handles, or coordinator capacity. Available capacity MUST be inherited from Node.js, the selected parser, the operating system, the filesystem, the browser, and the execution environment. The application MUST NOT inspect an unexpected failure's capacity, resource, or operational cause to reclassify, retry, or recover it; a failure not confined to one file fails the affected attempt, which commits no item, Source, recognition or derived result, scan-result body, success response, or generation. One closed cause check exists, at the single-file read boundary: the resource-exhaustion errno set — `EMFILE`, `ENFILE`, `ENOMEM` — identifies a condition of the machine rather than of the file being read, so such a failure routes to the attempt abort instead of becoming that file's per-file outcome (Constitution § Quality and Safety Standards). No other errno, message, or cause inspection exists. If work completes after its request loses publication authority through disable, shutdown, supersession, or failure, every late result MUST be discarded. Engine or operating-system termination is an environment limitation and MUST NOT be represented as a product guarantee.
- **FR-030**: Users MUST be able to rescan the active sources explicitly. Every admitted scan command MUST receive an opaque `scanRequestId`; every queued, active, complete, partial, or failed status MUST identify that request; and a successful generation MUST record the request that committed it. A prior status, snapshot, or generation MUST NOT satisfy completion of a newer request. Public `partial` MUST mean only the file-confined `partial` outcome in the Closed Scan Publication Outcomes table; no other incomplete state may be published. Repository and Global inspection keep independent generation sequences because their lifecycles are independent: the Repository sequence starts at bootstrap generation 0, while a Global sequence exists only from the enable commit that creates it until disable discards it. Scan results MUST be committed atomically as one generation snapshot of the owning sequence. A successful complete or partial commit MUST replace that sequence's previous snapshot and invalidate that sequence's previous-generation `FileDetail`, comparison selection or view, and editor-model state, which MUST NOT be restored from a stale response; a commit MUST NOT modify or invalidate the other sequence's state. A file's identity is its Source and Source-relative Path — stable across generations, so no per-generation file ID exists — and a detail request resolves that identity against the current committed snapshot: it serves the file the current generation holds at that path, or reports that it holds none, never a previous generation's record. If a rescan fails fatally before commit, the inspector MUST discard all of that scan's uncommitted results, including partial results, retain the last successfully committed snapshot, mark it as stale for that Source because the rescan failed, and show the failed request's error. An all-rejected Global attempt MUST produce no commit.
- **FR-031**: Inspection results MUST remain session-scoped by default and MUST NOT be persisted as a profile, cache, or repository file by the initial release.
- **FR-032**: Across inventory, detail, comparison, Global controls, diagnostics, API responses, CLI output, and documentation, the initial release MUST NOT act as a validator, linter, natural-language semantic analyzer or ranker, synchronizer, converter, formatter, auto-fixer, policy engine, or remediation adviser. It MAY perform only syntax-only parsing, reading the values a parser resolves for the declarations the recognized kind publishes, serialization of those resolved declarations into the documents its detail and comparison surfaces render (FR-007, FR-011, FR-012), classification against frozen documented fields and rules, and projection of documented order, scope, condition, selection, and reference relationships. Those operations MUST NOT decide or imply correctness, effectiveness, compliance, quality, or support beyond the frozen catalogs, and parse diagnostics MUST remain descriptive failures rather than validation findings.
- **FR-033**: Customization file source text and the declared name MUST be presented as inert text or inert data; embedded markup, images, links, URI handlers, control sequences, or other content MUST NOT execute, load, or navigate merely because the customization file is displayed.
- **FR-034**: The inspector MUST NOT attach a Claude Code recognition to `AGENTS.md` solely because of its filename, infer that an unreferenced script in `.claude/hooks` is a hook, or treat a standalone `.claude/prompts` directory as a supported Claude Code customization file type.

For the Global `AGENTS.override.md`/`AGENTS.md` branch, empty MUST mean that the decoded non-binary string has `String.prototype.trim().length === 0` after one optional leading UTF-8 BOM is removed; whitespace-only text is empty, while a retained `U+FFFD` is non-whitespace. The fallback applies when the override is absent or empty; a binary or unreadable override ends the branch with its diagnostic and no fallback. - **FR-038**: All executable application code in the initial-release implementation and package MUST be JavaScript/TypeScript. The CLI, local host, and inspected-source filesystem layer MUST run on Node.js public JavaScript APIs, and browser logic MUST be generated from JavaScript/TypeScript sources. Declarative generated HTML/CSS, strict JSON manifests, documentation, and license files MAY be packaged. The product MUST NOT contain Rust code, Node-API or other native addons, prebuilt native binaries, package-lifecycle compilation, or package-lifecycle/runtime artifact downloads. The closure guarantees are established against the committed lockfile’s pinned resolution and audited at release; the published package carries no lockfile, so a consumer install resolves the caret ranges freshly, and a dependency version outside the audited resolution is a recorded residual limitation (research.md § 3) rather than a certified property of every later install.

Membership MUST be decided by bundling rather than by which manifest section declares a package: a dependency whose client half is bundled belongs in the file, and one the package manager installs for the user to load at run time MUST NOT be repeated there, because its own license file arrives with it and a second copy can only go stale. - **FR-044**: The bundled browser MAY keep, on the reader's own machine, preferences about how that reader wants this application presented and how their machine handles a file — which application a detail surface opens a file in, and which colour scheme the page is drawn in — and nothing else. Such a preference MUST hold no inspected value: no Source root, Source-relative Path, authored name, file content, or session identity, so the FR-027 purge and the FR-031 session scope continue to describe every inspected value the client holds. ### Key Entities

- **Inspection Session**: The transient user activity containing exactly one Repository Source created during bootstrap without filesystem I/O from the selected Repository root defined by FR-001, zero to three tool-specific Global Sources, current scan results, comparison selection, and diagnostics.
- **Scan Request**: One admitted Repository initial scan or explicit rescan, or one nonempty initial-enable/retry `GlobalBatchScan`, identified by one opaque `scanRequestId`. A deterministic all-rejected Global initial attempt or retry is `active-no-job` and creates no Scan Request. A Global batch uses one request for all of its admitted tool roots rather than one request per Source. Every Scan Request's status and successful committed generation remain request-correlated so an older snapshot or status cannot satisfy a newer request.
- **Source**: An explicit source identity with a kind (`Repository` or `Global`), exactly one root location, enabled state, and scan status. The Repository Source exists at session bootstrap with a stable `sourceId` and an escaped root label. A Global Source is created only by its atomic post-consent commit and is additionally identified by exactly one supported tool; customization files of different types within that root remain separate inventory items.
- **Source-relative Path**: A customization file's display, filtering, lookup, and selection path relative to the one root of its owning Source — the exact raw entry names joined with `/`. It is repository-relative to the selected Repository root only for the Repository Source; each Global Source uses its own root and namespace.
- **Customization File**: One discovered file within a Source, identified by its Source-relative Path, with its encoding — which also determines the derived read state — complete source text when readable, recognitions, relationships, and diagnostics.
- **Tool Recognition**: A tool-specific interpretation attached to a customization file, including tool, file type, the declared name, and its extraction outcome.
- **Evidence Assessment**: The atomic evidence state for one exact behavior, rule, or strategy subject — its closed documentation completeness and its ordered lifecycle qualifiers, kept separate and never reduced to one scalar or a qualifier union. It lives on the registry record it grades as a maintenance fact; no response, provenance, or relationship carries one, because the product reports what it found rather than how well a vendor documents its rules.
- **Relationship**: A non-executed reference from a customization file to another path or declared component, including boundary and resolution status without imported content expansion.
- **Diagnostic**: A session-only, actionable explanation of an empty result, deterministic malformed or binary content outcome, uncertainty, stale file, cycle, or boundary violation that does not duplicate customization source values. It has exactly one location scope. A file-scoped Diagnostic MUST require a coherent `sourceId` and `sourceRelativePath` pair: the file MUST belong to the identified Source, and the path MUST be that file's path within that Source. A source-scoped Diagnostic MUST require only `sourceId` and MUST forbid `sourceRelativePath`. There is no pathless scope: every Diagnostic MUST belong to a Source. This location scope is independent of whether the Diagnostic belongs to a committed generation or to the session lifecycle. An unexpected failure that is not confined to one file surfaces as an ordinary error and does not become a Diagnostic.

## Assumptions

- The initial release is a local, single-user inspection session; remote hosting, collaboration, accounts, and durable profiles are outside scope.
- All executable application code in the initial release is JavaScript/TypeScript: the browser runs generated client logic and declarative assets, and all non-browser product code runs on Node.js. Strict manifests, documentation, and license files remain non-executable package data. Per FR-038, users of the published package need no Rust toolchain, native compiler, native addon, platform-specific prebuilt binary, or package-lifecycle/runtime artifact download: the published package payload and the product runtime contain and require none of these. The one recorded closure exception is the `open` package's vendored POSIX-shell `xdg-open`, which the package's own selection policy uses on a Linux host whenever the vendored copy is executable, falling back to the system `xdg-open` otherwise (FR-038). Development-only tooling is outside the published package payload and outside this guarantee; contributor toolchains use separately pinned and audited third-party development dependencies that may include prebuilt platform-specific components or pinned certification-browser downloads, and none of these may enter the published payload or product runtime.
- Inspected Repository and opted-in Global roots are ordinary local paths controlled by the initiating user, in a workspace the user already trusts. Normal concurrent edits may surface as per-file diagnostics or a failed scan; the user rescans. The product does not defend against an adversarial local process, because a user who does not trust the workspace should not run the tool there.
- Product-issued source mutation is measured by mutation-capable filesystem requests and observable source properties, not by operating-system access-time policy. The Inspector never requests access-time changes; an OS-only read-side access-time update is recorded separately and does not establish a product mutation.
- The selected Repository root is the inspection boundary, not proof of the effective working directory used by any coding agent. Selecting a subdirectory through the invocation `cwd` or `--root` limits the Repository Source to that subtree; users rerun the command from the intended root or supply that root through `--root` to inspect a broader scope.
- Official customization formats can change. Their exact inspection paths, filenames, and extensions will be revalidated and frozen during planning, then published and covered by conformance fixtures. When a versioned release note directly adds behavior that a current general guide's exhaustive list omits, the specific addition remains in scope while the incompatible evidence is retained as `conflict`; unmentioned schema or ordering is not inferred.
- Official pages can be undated or rolling, and upstream features can be previewed, rolled back, or superseded. Evidence freshness is fixed by per-record `reviewedOn` dates and section fingerprints rather than page dates, and an undated or rolling page never establishes a version gate. A previewed feature keeps its closed `preview`/`experimental` lifecycle qualifiers; a rolled-back or superseded assertion is re-reviewed on drift and is removed or retained as `conflict` when directly contradicted. Neither state is presented as `stable` or resolved by inference.
- Global inspection covers only the instruction paths in FR-015 through FR-017; additional user-global skills, agents, settings, MCP definitions, plugins, managed configuration, and remote configuration require separate consent and future specification work.
- Source text, the displayed declared name, authored relationship targets, and comparison content are presented without credential masking so authored differences remain visible. Environment-variable references in inspected content remain literal and are not resolved; the product has no reveal workflow. The loopback-bound local host is the API access boundary and the whole boundary; no confirmation step stands in front of authored content and no notice stands beside it. The bundled browser holds the content in memory only and drops it on the client-data purge.
- The inspector may perform syntax-only parsing, reading the value a parser resolves for a declaration the recognized kind publishes, frozen-catalog classification, and projection of documented structural order, scope, condition, selection, and reference relationships. It does not interpret natural-language meaning, determine correctness, effectiveness, compliance, or quality, rank content, or advise remediation; a parse diagnostic is a descriptive failure, not a validation result.
- File, collection, parser, transport, queue, time, and concurrency capacity is inherited from Node.js, the parser, the operating system, the filesystem, the browser, and the execution environment. The Inspector defines no numeric capacity ceiling and never inspects a thrown or rejected operation to classify its cause or to classify customization content as valid or invalid.
- Public Node.js filesystem promises may not be force-cancellable. Disable, shutdown, or supersession revokes publication authority and discards late results. The product does not promise physical cancellation of kernel I/O or process survival after an uncaught startup error.
- Comparisons are limited to two distinct customization files at a time in the initial release and do not merge or edit content.
- Product documentation and the supported matrix will use official vendor documentation as the normative external dependency; undocumented behavior will remain explicitly uncertain.
