### Session 2026-07-15

- Q: What establishes the Repository source root? → A: The selected Repository root: the exact process working directory returned by the one `process.cwd()` capture when `--root` is omitted, or the one `--root` value — kept as given when absolute and otherwise resolved lexically against the capture with the active platform's `node:path.resolve`. The initial release has no separate repository picker or ancestor-root discovery.
- Q: Which term should describe the first product scope? → A: Use “initial release” throughout the specification.
- Q: What should the specification call a discovered agent-customization file? → A: Use “customization file” throughout the specification.
- Q: What should the specification call the documented set of filesystem paths eligible for inspection? → A: Use “inspection path allowlist” throughout the specification.
- Q: How must vendor lookup tables and their evidence be organized? → A: Keep vendor lookup behavior separate from Inspector matchers and runtime composition; use separate product documents, separate Repository and User/Global tables, separate GitHub Copilot VS Code/CLI/Cloud tables, and stable official-source references for every maintained row.

### Session 2026-07-16

- Q: What runtime implementation constraint applies to the initial release? → A: Implement all executable application code as JavaScript/TypeScript. The CLI, local host, and inspected-source I/O run on Node.js public JavaScript APIs, while the browser receives generated JavaScript plus declarative HTML/CSS assets; strict JSON manifests, documentation, and license files remain valid package data. Do not use Rust, Node-API or other native addons, prebuilt native binaries, package-lifecycle compilation, or package-lifecycle/runtime artifact downloads.
- Q: What filesystem-race guarantee is possible under that Node.js-only constraint? → A: Centralize inspected-source I/O in one Node.js module, reject links and boundary failures exposed by public Node.js APIs, compare root, ancestor, candidate-path, open-handle, and post-read identity, canonical-location, and metadata snapshots, and discard all candidate bytes when a mismatch is detected. Use `O_NOFOLLOW` as final-component defense in depth when Node.js exposes it and the platform enforces it. The threat model excludes an adversarial local process that races a source root or ancestor or, where effective `O_NOFOLLOW` is unavailable, final path component between these non-atomic checks; public Node.js APIs also cannot reveal every same-device mount or reparse behavior. These residual risks and their Node.js or operating-system resolution paths must remain documented.

### Session 2026-07-17

- Q: How are user-global roots represented as Sources? → A: Represent each admitted member root as its own Global Source—Codex at `CODEX_HOME`, Claude at `CLAUDE_CONFIG_DIR`, Copilot at `COPILOT_HOME`, and the shared agent home at the derived `.agents` path (FR-045)—so a session has zero to four Global Sources. A Source has exactly one root; customization files of different types within that root remain separately visible.
- Q: How should literal credentials and environment-variable references in customization files be presented? → A: Display source text, displayed declared metadata values, authored relationship targets, and comparison content as authored without credential masking or a reveal workflow so literal differences remain visible. Treat environment-variable references in inspected content as literal text and never resolve or substitute their process values; the documented tool-home environment variables are used only to locate Global roots. Show the file directly — no warning, acknowledgement, or notice precedes or accompanies it (FR-027) — while keeping operational diagnostics and logs free of duplicated source values.
- Q: What happens to the previous inventory when an explicit rescan fails fatally? → A: Keep the last successfully committed snapshot visible, label it as stale because the rescan failed, and show an actionable failure diagnostic. Discard every uncommitted result from the failed scan, including partial results, and replace the retained snapshot only after a later rescan commits successfully.
- Q: What path term applies consistently across Repository and Global sources? → A: Use “source-relative path” for the path from a customization file's owning Source root. For the Repository Source this is relative to the selected Repository root; for each Global Source it is relative to that tool's admitted home root. Use “repository-relative path” only when discussing the Repository Source specifically.
- Q: What counts as a critical usability issue for SC-006? → A: A problem is critical if it prevents completion of a primary workflow without prohibited assistance or causes an unsafe behavior such as unintended execution, inspected-source mutation, a prohibited direct product-issued outbound request or MCP connection as defined by FR-022, or exposure of inspected content to another machine. The two exact internal loopback HTTP classes authorized by FR-022 are neither outbound nor MCP connections and are not this automatic event. Recorded OS-mediated traffic for a pre-mounted or mapped source remains the FR-022 platform/environment limitation rather than this automatic connection event.

- Q: What does it mean for Repository results to remain unchanged when Global enablement commits? → A: The Repository Source keeps its stable `sourceId`, and its customization-file membership, source-relative paths, readable or diagnostic states, recognitions, relationships, Repository-scoped diagnostics, and authored source text remain semantically unchanged because that operation does not rescan the Repository. Every successful initial or retry Global Source commit advances only the Global sequence's generation and invalidates only its previous-generation `FileDetail`, comparison selection or view, and editor-model state; the Repository sequence's views are not invalidated (FR-030). Those Global-sequence user-interface lifecycle changes are not semantic changes to Repository results. An all-rejected attempt produces no Global Source commit and is outside this rule.
- Q: What location context does each Diagnostic carry? → A: Every retained Diagnostic has exactly one scope. A file-scoped Diagnostic requires a coherent `sourceId` and `sourceRelativePath` pair in which the file belongs to that Source and the path is that file's path within the Source; a source-scoped Diagnostic requires only `sourceId` and forbids `sourceRelativePath`. There is no pathless scope: every Diagnostic the product produces belongs to a Source. Scope describes location independently of whether the Diagnostic belongs to a committed generation or the session lifecycle.
- Q: What counts as an inspected-source mutation? → A: Count product-issued requests to write, truncate, create, rename, delete, link, change mode or ownership, set times, extended attributes, or ACLs, or open with mutation-capable flags. The Inspector issues none. A read-side access-time update performed solely by the operating system is outside product control and is not counted as a product-issued mutation; tests record it separately, never request it, and never use it as evidence that the Inspector mutated the source.
- Q: What structural interpretation is allowed without making the Inspector a semantic analyzer? → A: Allow syntax-only parsing, reading the values a parser resolves for the declarations the recognized kind publishes, classification against frozen documented catalogs, and projection of documented order, scope, condition, selection, and reference relationships. Across inventory, detail, comparison, Global controls, diagnostics, API responses, CLI output, and documentation, do not interpret or rank natural-language meaning, decide correctness, effectiveness, compliance, or quality, or provide remediation advice.
- Q: Is sensitive-content acknowledgement an API authorization factor? → A: No. The loopback-only bind of the unauthenticated session host is the access-control boundary. No acknowledgement gate exists (2026-07-28): standing in front of a loopback-only session showing the viewer their own files, it guarded nothing while making every file take two interactions to read. A detail or comparison surface shows the file exactly as written; it neither asks first nor carries a notice about what the content may contain, which would spend the screen telling a reader about their own repository. What survives is the handling: authored content is held in browser memory only, is reachable only by an explicit request for one file or one comparison, and a client-data purge is the central full-session client reset that clears inventory, detail, comparison, editor models, and in-memory metadata after document-liveness failure or an equivalent terminal reset. The Global-disable action MUST perform that purge before sending its request, and observation of a greater Global content epoch or a non-null disable fence MUST repeat it before rendering. Closing a route, ordinary file or Source removal, or changing generation may instead dispose only the affected models and is not by itself a client-data purge.
- Q: Does the Inspector define file-size or item-count validation limits? → A: No. File and collection capacity is determined by Node.js, the parser, the operating system, the filesystem, the browser, and the execution environment. The Inspector does not reject or classify customization content by a product-defined size or count ceiling. A failure confined to one file surfaces as that file's Diagnostic (FR-028); any other thrown exception or rejected operation aborts the affected publication attempt — the file and scan layers never inspect its cause to reclassify, retry, or recover it, and the one closed cause check is the resource-exhaustion errno set (`EMFILE`, `ENFILE`, `ENOMEM`) that routes a read failure to this abort instead of into a per-file outcome; that attempt commits no item, Source, recognition or derived result, scan-result record or success response, or generation, never authorizes a partial generation, and leaves only any prior committed snapshot available.
- Q: When may a scan publish a partial generation? → A: Only after complete traversal and generation assembly when one or more published files produced an FR-028-eligible deterministic, non-throwing entry-local outcome as data while unaffected files remain complete. A published file is an admitted candidate or a file a companion census listed beside one; being listed is not being admitted, but it is read the same way. A failed read counts the same for both. A companion whose bytes are binary is the ordinary published fact of an asset — nothing expected it to be text — so it carries no Diagnostic and makes nothing partial, where an admitted candidate's binary content stays diagnostic-only because a rule admitted that file as a text customization (2026-07-29). Complete outcomes such as readable `utf-8-replaced` text are expressly excluded from that partial condition. A read, decode, parse, or extraction failure at the single-file boundary becomes that file's contracted entry-local outcome (FR-024/FR-028 and the Closed Scan Publication Outcomes table), classified by where the failure occurred rather than by inspecting its cause. A recoverable environment or resource failure is not such a failure even when it surfaces during one file's read: it is a fact about the environment rather than about that file, so calling the file unreadable would report a condition of the machine as a property of the user's content. Any exception or rejected operation outside that single-file boundary — from coordination, assembly, serialization, transport, or lost authority — is never converted into an entry outcome and never authorizes partial publication. A recoverable environment or resource failure aborts the whole publication attempt and publishes nothing (Constitution § Quality and Safety Standards).
- Q: How are read bytes decoded? → A: Any NUL byte classifies the file as binary — for an admitted candidate that classification is diagnostic-only, while a census-listed companion's binary bytes are its ordinary published fact. Otherwise decode once as UTF-8 using replacement semantics, recording and removing one leading BOM when present. When invalid byte sequences are replaced with `U+FFFD`, record `utf-8-replaced` and pass that exact garbled decoded string through display, parsing, extraction, and comparison. Never detect or retry another encoding.
- Q: Does an absolute Global root outside the ordinary home fail merely because of its location? → A: No. An absolute configured root (active-platform `node:path.isAbsolute`) is eligible for post-consent admission even when it is outside the ordinary home. Absence selects the documented default; empty, relative, invalid, or inaccessible roots follow the closed outcomes below and never create fallback authority.
- Q: How are the release-evidence denominators for SC-003, SC-004, SC-005, and SC-007 frozen? → A: A checked-in, versioned release-evidence fixture manifest assigns stable case IDs, required classes, fixture or builder references, expected outcomes, and content digests to those criteria. The manifest version and digest identify the exact denominator used for a release candidate; a missing case, unexecuted case, digest mismatch, or empty required class fails the affected criterion. Removing or reclassifying a case, changing a required-class definition, or changing an expected outcome requires an explicit manifest-version increment and review rather than silently weakening the denominator. A fixture-byte-only change instead requires both the referenced-fixture digest and canonical manifest digest to change. Either kind of change starts a new non-comparable measurement set.

### Session 2026-07-20

- Q: Does generation 0 require filesystem admission before the Repository Source exists? → A: No. Session bootstrap MUST capture the invocation working directory from `process.cwd()`, select the Repository root from that string or a valid `--root` value using lexical path operations only, and create exactly one Repository Source synchronously with zero filesystem I/O. Its escaped root label and stable `sourceId` are non-authorizing session identity only; the first scan simply reads the retained raw selected root — there is no separate admission layer. A deterministic scan failure — including a root that does not exist or cannot be read as a directory — leaves that Source present with failed scan status, retains its source-scoped `root-unreadable` Diagnostic (FR-002), and publishes no customization files or generation. A thrown or rejected automatic-startup operation instead propagates to the process top level and may end the process or session.
- Q: How may a user select a Repository root other than the invocation working directory? → A: The CLI MUST accept `--root <path>`. When omitted, the selected Repository root is the exact string from the one `process.cwd()` capture. An absolute option is kept as given, and a relative option is resolved lexically against the captured invocation directory with the active platform's `node:path.resolve`. A repeated `--root` resolves to the argument parser's last value (deterministic last-wins) and is not separately rejected — repeated-argument policy belongs to the argument parser. An explicit empty value MUST produce a fixed actionable, source-value-free startup error and exit before creating a session or opening a browser. A missing value MUST be rejected at the same boundary by the argument parser's typed validation; the product MUST NOT duplicate that parser-owned check. Root selection itself MUST perform zero filesystem/network I/O, and the rejected launch MUST perform no invocation-`cwd`-, `--root`-, or selected-root-derived I/O and no DNS, SMB, or outbound-network call. The selected root's readability is established only by the first scan, which fails with the source-scoped `root-unreadable` Diagnostic when the root does not exist or cannot be read as a directory.
- Q: Which tools does one Global-inspection consent enable? → A: Consent is session-wide, not tool-selective. Before consent, the product performs no proposed-root filesystem I/O. After one explicit Global opt-in, one transaction MUST attempt all four frozen preview entries and automatically include every root that is structurally present and passes admission. The user cannot select or deselect individual members. A lexically invalid root, an exact structural `lstat` absence, or a deterministic link/type/boundary rejection creates no Source and does not block the admitted subset; all admitted Sources publish together in one atomic generation. Any thrown or rejected operation not confined to one file aborts that transaction as the failed request's ordinary error and commits none of its subset. If no root is admitted and no operation throws or rejects, the transaction uses the documented all-rejected outcome.
- Q: How are the Global root inputs captured consistently across platforms? → A: On each request that creates a new unconsented preview, read `COPILOT_HOME`, `CLAUDE_CONFIG_DIR`, and `CODEX_HOME` exactly once each in that fixed order. A value is absent only when the captured value is `undefined`; an empty string is a present override. Call the imported `node:os.homedir()` exactly once for that request, lexically append `.copilot`, `.claude`, or `.codex` with the active platform's `node:path.join` for each absent value, and always append `.agents` the same way for the shared agent home, which has no environment setting. Do not separately choose among `HOME`, `USERPROFILE`, or another platform variable. This capture performs no filesystem operation or existence check. Any throw/rejection during environment capture, `homedir()`, joining, retention, escaping, or preview serialization fails that invocation with its ordinary real error at the session RPC boundary and creates no preview or authority. A successfully created preview freezes all four exact strings and is never recaptured while active consent uses it.
- Q: How are root strings classified, displayed, and bound without Unicode or escape ambiguity? → A: Assign Global state in order: a present environment string of length zero is `present-empty`; a string containing U+0000 or an unpaired UTF-16 surrogate is `invalid`; otherwise active-platform `node:path.isAbsolute` false is `relative`; and a remaining absolute spelling is `eligible` — the platform's own path handling owns spelling semantics. For every Repository or Global root label, iterate exact UTF-16 code units without normalization: copy only ASCII letters, digits, `.`, `/`, `:`, `_`, and `-`; encode every other code unit as `\uXXXX` with four uppercase hex digits, including each surrogate half and every backslash. Render that ASCII result as text, never HTML, and never decode it for I/O. A preview is the one server-retained record identified by its opaque `previewId`, and what would be read below an admitted root is bound by the digest-free `allowlistVersion`/`traversalPlanVersion` pair; the pair carries no digest because the server never re-verifies its own retained state cryptographically.
- Q: Who handles a runtime file-read error? → A: A failure confined to one file becomes that file's per-file Diagnostic (FR-024/FR-028). Any other rejected Node.js operation is not caught by the file, parser, recognition, or scan layers to classify, retry, or recover; it propagates to the execution boundary that owns the trigger. For a session-API-owned operation, the failed request reports its real error ordinarily — directly if the request has not been accepted, or retained per FR-030 as the terminal error of the already accepted job — and the process and prior committed snapshot stay available. For an automatic startup operation with no request owner, the error propagates to the process top level and the product does not promise process survival. Neither path commits a failed-attempt item, result body, or generation.
- Q: How can expected absence coexist with runtime-owned file-read errors? → A: Only the probe of a contract-declared exact target (the Global exact-file rules, including the Codex override/fallback pair) MAY treat a missing entry (`ENOENT`/`ENOTDIR` from the existence probe) as the closed `absent` outcome. This narrow conversion MUST NOT inspect the message, infer another cause, or apply to any other code or operation. A read failure after discovery — including a broken symbolic link — is that file's `file-unreadable` Diagnostic (FR-024); there is no `entry-disappeared` or race-detection taxonomy.
- Q: What happens to non-NUL bytes that are not valid UTF-8? → A: Process the replacement-decoded garbled text as-is. Decode once with UTF-8 replacement semantics, preserve every resulting `U+FFFD` in `sourceText`, label the encoding `utf-8-replaced`, and continue ordinary parsing, extraction, display, and comparison. This decode outcome is complete rather than partial by itself. Do not guess a source charset or try a second decoder. A NUL-containing admitted candidate remains `binary`, diagnostic-only, and a file-confined `partial` outcome; a census-listed companion's binary bytes are its ordinary published fact.
- Q: How are Unicode-normalization collisions and multiple hard-link paths represented? → A: For an enumerated path, retain the exact raw entry-name segments returned by `Dirent.name`; for a targeted fixed path that intentionally performs no parent enumeration, retain the exact immutable registry target spelling. That provenance-specific spelling is both the filesystem operand and — joined with `/` — the public Source-relative Path used for matching and display: nothing is normalized away, a filesystem holds one entry per name so every published path is unambiguous, and presentation escapes control characters without changing the stored value. Distinct allowlisted paths that happen to be hard links to the same underlying file are ordinary independent files: no physical-identity grouping, primary-path selection, or alias list exists, and each path publishes its own Customization File (FR-024). Symbolic links are read transparently, and identity is never merged across Sources.
- Q: What exactly counts as an empty Codex override for fallback selection? → A: Only a safely verified and read non-binary `AGENTS.override.md` whose decoded string has `String.prototype.trim().length === 0` after recording and removing one optional leading UTF-8 BOM is empty. Whitespace-only text is empty. A safely read `utf-8-replaced` string follows the same test, so any retained `U+FFFD` makes it non-empty. Only a missing initial target (`ENOENT`/`ENOTDIR` from its existence probe) counts as absent and permits fallback; an unreadable or binary override — including a broken link or a read that fails after the probe — ends the branch with its file Diagnostic (`file-unreadable` or `file-content-binary`) and no fallback.
- Q: How is VS Code 1.118+ workspace-root `.mcp.json` handled while the current MCP guide still omits it? → A: Admit the exact root file as a second compatible Copilot/MCP provenance on the same physical file already eligible for CLI recognition. The 1.118 release note establishes only the VS Code path and a most-specific same-name rule; the current guide still documents `.vscode/mcp.json` as the workspace `servers` file and does not establish the root-file schema or a total order. Preserve `documentationStatus: conflict`, add no VS Code-owned root extractor fields, and retain selection as unknown until direct official documentation resolves it.

### Session 2026-07-21

- Q: What does an active-consent Global retry target, and what state may it replace? → A: It reuses the same frozen preview, consent record, and fixed ordered tuple `[copilot, claude, codex, agents]`. Retry is offered only after the matching preview is verified, `globalEnableInProgress` is null, `pendingTools` is empty, and `retryableTools` is nonempty. The server derives the complete fixed-order `retryableTools` set: non-pending unpublished `admitted` controls plus `rejected` controls whose `retryDisposition` is `same-preview`; published, pending, and lexical `new-preview-required` controls are excluded, and neither the UI nor API may add, omit, or reorder a target. During tentative validation/admission only authority-free `globalEnableInProgress` becomes newly visible; every existing Repository and Global Source, control, batch/diagnostic field, `pendingTools`, `retryableTools`, and the prior committed snapshot retain their exact pre-operation projection. If every retry target is deterministically rejected, atomically update those controls and return `active-no-job` without a `scanRequestId`, scan job, Source, generation, or existing-Source replacement. If one or more targets are admitted, atomic queued acceptance creates exactly one `GlobalBatchScan` and one `scanRequestId`, changes `pendingTools` to exactly that admitted subset with matching `batchStatus`, preserves the existing Sources, and publishes all newly admitted Sources together in one atomic generation; a thrown or rejected operation is reported as the failed request's ordinary error and restores the exact pre-operation state.

### Session 2026-07-22

- Q: Are inspected customization files an adversary the product must defend against? → A: No. The tool runs in a workspace the user already trusts and simply shows what AI agents will read. Requirements derived from the adversarial-file model (TOCTOU checkpoint re-verification, race taxonomies, hard-link read-once grouping, the structural-`lstat` carve-out doctrine) are superseded by ordinary traversal and per-file diagnostics; earlier clarification entries remain as history. Retained: inspected content is never executed, the loopback session is protected from other origins, and displayed content is rendered inert.
- Q: Is a symlinked customization file read or only reported? → A: It is read transparently, like any other file: agents resolve symbolic links when they load customization files, so faithful inspection must show the linked content. A link whose target is missing or unreadable yields the ordinary per-file diagnostic, and recursive traversal tracks visited directories by real path so a link cycle cannot prevent scan termination. The interim symlink-not-followed rule and its `file-symlink` diagnostic are removed.
- Q: What implements the local host, and how is the session protected? → A: The product adopts the devframe local-tool framework — the same foundation eslint/config-inspector uses — for static asset serving and the local session API channel, with devframe authentication disabled. Protection is loopback binding only: the host binds the loopback interface and the session is never exposed beyond the initiating machine. The per-session token, product-owned Origin checks, and the hand-written HTTP router are removed; the residual exposure of an unauthenticated loopback host (other local processes, DNS rebinding) is a documented limitation. Constitution v3.0.0 records the amended obligation.
- Q: Are operational-log content rules and the generic error envelope still required? → A: No. FR-040 and FR-041 are removed. The product has no telemetry (FR-022 already forbids outbound traffic), terminal and UI output are read by the same user who owns the inspected files, and the unauthenticated session API already serves complete file content — so hiding error causes protected nothing while making failures undebuggable. Errors are reported ordinarily (real messages, ordinary propagation), and no closed error entity, sanitizer, or envelope exists. Failure semantics stay where they already live: per-file isolation in FR-028, atomic commit/stale-snapshot rules in FR-030, and the scan-publication table. Constitution v4.0.0 records the removal.
- Q: Do Repository and Global inspection share one generation sequence? → A: No. Their lifecycles are independent — the Repository Source always exists, while Global sources exist only between enable and disable — so each keeps its own atomic generation sequence: the Repository sequence from bootstrap generation 0, and a Global sequence created by the enable commit and discarded by disable (which commits nothing). A commit invalidates only its own sequence's views. The former carry-forward rules — a Global commit preserving the Repository inventory unchanged by copying it — are removed. Cross-source comparison is unaffected: it always compares each source's last committed state.

### Session 2026-07-23

- Q: Which host name does the local session host bind and display? → A: The fixed host name `localhost`: the host binds the loopback interface through it (the platform resolver yields IPv4 `127.0.0.1` or IPv6 `::1`), and the printed and auto-opened URL is `http://localhost:<port>/`, which users recognize more readily than a numeric address. ### Session 2026-07-29

- Q: Do public Source-relative Paths normalize the raw entry names? → A: No. The published path is the exact raw entry names joined with `/` — the spelling an agent reading the same tree operates on — and presentation escapes control characters without changing the stored value. There is no derived NFC display spelling and no normalization-collision concept: a filesystem holds one entry per name, so every published path is unambiguous, and two raw spellings that would render alike are two real files published apart. The `path-normalization-collision` Diagnostic and the pathless `session` scope go with it. The NFC derivation served only the rendering of NFD-spelled entries left by normalization-preserving filesystems; it rewrote the identity this product exists to show faithfully, and the rejection machinery it required withheld real files from the inventory.

### Session 2026-08-08

- Q: What names a skill inventory row? → A: The name each recognizing tool's own documentation invokes the file by, making the row's unit one invocation name as one tool resolves it. Codex and Copilot invoke the authored frontmatter `name`; Claude Code derives its command from the skill directory whatever the frontmatter declares, prefixed for a nested skill with the root-relative `/`-joined path of the directory holding its `.claude` and a `:`, so `apps/web/.claude/skills/deploy/SKILL.md` declaring `name: ship` is `apps/web:deploy` on its Claude Code row and `ship` on its Copilot one. One file whose recognizing tools invoke it by different names appears as a definition of each name's row. A file that declares no name — or declares it empty — is invoked by its skill directory, which is where Claude Code's command name comes from anyway, so every row has a name and two such files in same-named directories share one.
- Q: When is a nested Claude Code skill's name qualified? → A: Always, with the prefix relative to the selected root. The vendor qualifies on a name clash with a prefix relative to a session working directory, but the inspector observes no session, and whether an unqualified name is free depends on user- and enterprise-level layers it never reads, so the root-relative qualified spelling is the one stable name a static inventory can stand behind (skills page § How a skill gets its command name).
- Q: What names the skill detail heading? → A: The skill's own directory, with the name each recognizing product invokes it by beneath. A detail URL is `/skills/detail/<source>/<source-relative path>` — the file's own identity, each path segment percent-encoded — so which document the page shows, its companions included, is the link's identity rather than a preference the page applies. No tool segment: two products reading one `SKILL.md` read the same bytes, so a per-product address would give one document two URLs differing only in a name, and the page states the name each product invokes the skill by instead. That identity is stable across rescans and server launches — it is the URL's path half: the Source-relative Path is the file's identity on the wire — no per-generation file ID exists — and a detail request resolves it against the current committed snapshot (FR-030), so a bookmarked link's path keeps naming the same file across rescans and across launches that select the same root — the path is Source-relative, and a launch that selects another root (FR-001) resolves it against that root's scan. Whether the whole bookmark resolves is the origin's question: the origin is devframe's port selection, which reuses the preferred port — the launch's `--port` when it states one, devframe's own default otherwise — when free and moves to another only when that port is occupied (quickstart.md), so a moved port changes where a bookmark points, never which file its path names. _(amended 2026-08-25: a launch can now state a preferred port, so what is reused is the preference rather than the default alone.)_ A path the current scan does not hold is reported as a dead link rather than resolved to a neighbour.

- Q: Is the comparison surface shared across customization kinds? → A: No. A comparison surface is kind-specific. ### Session 2026-08-18

- Q: What does an instructions inventory row list? → A: One applicability range and the instruction files that govern it. The range is a glob relative to the Repository root, derived from the file's own path: the Repository root derives `**`, and a file in `packages/api/` derives `packages/api/**`, with a directory the recognizing product keeps that filename in stripped from the tail — Claude Code keeps `CLAUDE.md` at `.claude`, so `.claude/CLAUDE.md` derives the root's `**` like the `CLAUDE.md` beside it, while a `.claude/CLAUDE.local.md` keeps its directory and derives `.claude/**`, because the page names the `.claude` alternative for `CLAUDE.md` alone. What such a directory means is that product's own fact, so each product answers for its own rules. Rows are keyed by the exact derived glob and grouped by text equality: nothing parses a glob, normalizes its spelling, or decides whether two ranges overlap, so two ranges share a row exactly when they are spelled alike, and the derived spelling is one a product fixes rather than one chosen per file. A derived range escapes the characters a glob reads as syntax, so a `packages/[api]` directory publishes `packages/\[api\]/**` and denotes exactly that directory rather than a character class. A file that declares its own range — Copilot's `applyTo` — is keyed by that declared value instead of by its path, and the declared value is published as the parser resolved it — the value's own quotes and escapes resolved once, the same reading every declared value gets — with no escaping or normalization added by this product: the resolved value already is the author's pattern, and escaping it would turn it into a directory literally named that. Such a file that declares nothing a row can be keyed by — no declaration, an authored empty value, a list or mapping with no row spelling, or declarations that could not be read at all — has no known range: its vendor reads that filename's applicability from the declaration alone, so a range read off the path would state the widest governance for a file the vendor gives none. Those files share the one row that states no range is known, sorted after every ranged row, each file's own diagnostics saying why when the reason is a failed parse. A range states what a file governs and never what a session loaded: which product reads a file, and when, remains runtime this tool does not observe (FR-009). _(amended 2026-08-22: the declared-range half named a second declaration besides Copilot's `applyTo`; a Claude rule is its own kind whose row unit is the file and out of which nothing is read at all, so no declaration of its could key an instructions row.)_
- Q: Does the walk enter an installed dependency tree? → A: No. A directory named `node_modules` is never entered, at the Repository root and at any depth, alongside the `.git`, `.hg`, and `.svn` internals already excluded: a `node_modules` directory holds packages a package manager installed, so a customization file inside one belongs to the package that shipped it and is reproduced from the manifest and lockfile rather than authored in the repository under inspection. A product may still read such a file at runtime — Claude Code discovers a `CLAUDE.md` in any subdirectory it reads a file in — so the exclusion narrows what this product inventories rather than describing what an agent can load. `node_modules` is excluded by entry name and by nothing else, unlike the VCS internals, which are excluded on the resolved real path as well: reaching an object store is wrong however the walk got there, while a directory the repository placed at a path of its own is the repository's, whatever its link resolves to, so a symbolic link at an authored location is inventoried on that location's terms (FR-024). The names are exactly those four: no ignore file is read to decide any of it, because an ignore file states what its own tooling skips, which is a different question and a moving one; another ecosystem's installed-dependency directory arrives with the report that names it.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Discover Repository Customizations (Priority: P1)

A developer selects the intended Repository root by changing to it or supplying `--root <path>`, launches the inspector through `npx`, and receives a browser-based inventory of the customization files recognized for GitHub Copilot, Claude Code, and OpenAI Codex. The selected Repository root is always represented as its own Repository Source.

**Why this priority**: Finding the relevant files without running an agent is the smallest useful version of the product and the prerequisite for every later workflow.

**Independent Test**: Launch the inspector once with a fixture repository containing supported, unsupported, nested, and multiply recognized files as the invocation `cwd`, and once from another directory with that fixture selected by relative `--root`. Confirm that both runs select the same Repository root and that the inventory contains every supported customization file at an allowlisted inspection path, excludes unrelated files, and identifies its Repository Source, customization file type, source-relative path, and recognizing tools.

**Acceptance Scenarios**:

1. **Given** `--root` is omitted and the invocation `cwd` contains supported customization files for all three tools, **When** the user starts an inspection, **Then** the browser shows that directory as one Repository Source and an inventory that can be filtered by tool and customization file type.
2. **Given** the user launches from another directory and supplies a relative or absolute `--root`, **When** the user starts an inspection, **Then** the selected root is shown as the one Repository Source and the process working directory is unchanged.
3. **Given** `--root` has an explicit empty value or is missing its value, **When** startup parses the command line, **Then** an explicit empty value emits the fixed actionable, source-value-free error while a missing value is rejected by the argument parser's typed validation, and either exits before session creation or browser opening.
4. **Given** one physical `AGENTS.md` recognized by both Copilot and Codex, **When** the inventory is displayed, **Then** it appears once as a customization file with two distinct tool recognitions.
5. **Given** files outside the repository inspection path allowlist, **When** the repository is scanned, **Then** those files are not interpreted or presented as customization files.
6. **Given** no supported customization files, **When** the scan completes, **Then** the user sees a successful empty state that explains the supported scope rather than an error.

### Edge Cases

- The selected Repository root cannot be read, becomes unavailable after startup, or is not the root the user intended to inspect; the invocation `cwd` itself may also become unavailable before `process.cwd()` can be captured.
- A file at an allowlisted inspection path is a symbolic link (read through its target like any other file; a broken link yields a per-file diagnostic) or disappears between discovery and reading (per-file diagnostic).
- A supported filename contains invalid text encoding, malformed frontmatter or configuration, extremely long lines, or binary content, or the execution environment reports that it cannot continue processing the file.
- One customization file has multiple recognized file types or recognizing tools.
- A customization file references another file through an absolute path, `..` traversal, environment-variable text, or a chain of imports; the reference stays authored text and no target is opened.
- A configured tool home is missing, empty, relative, inaccessible, or outside the user's ordinary home location.
- A Global override file exists but is empty; the documented fallback file may then apply.
- Files change while the browser is open, including sensitive content becoming newly present.
- An explicit rescan fails fatally after producing partial results; the partial results are discarded and the last successfully committed snapshot remains visible with a stale marker and failure diagnostic.
- A browser session is refreshed or opened from a host other than the initiating machine.
- A customization file contains a literal credential or an environment-variable reference whose variable is set in the Inspector process; the literal source is displayed without masking, and the reference is not resolved or substituted.
- A read causes the operating system to update access time even though the Inspector issued no mutation-capable filesystem request; that OS side effect is recorded separately and does not fail the product-issued-mutation assertion.
- An admitted operation fails unexpectedly during I/O, decoding, parsing, assembly, or transport: a file-confined failure becomes that file's diagnostic (FR-028); anything else fails the attempt while the last committed snapshot stays visible and the failure is reported as an ordinary error.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: Users MUST be able to launch the product through `npx` and open the resulting local inspection session in a browser. The CLI MUST capture `process.cwd()` exactly once and accept `--root <path>`; an absolute option is kept as given and a relative option is resolved against the captured invocation directory, and the result is the selected Repository root. When `--root` is supplied more than once, the argument parser's last value is the selected root (deterministic last-wins), which the product does not separately reject — repeated-argument policy belongs to the argument parser, and Gunshi resolves a repeated scalar option to its last value. The affected item MUST retain enough source-relative path and Source context for the user to resolve the problem. A parser or extractor failure MUST keep the complete readable source (including any replacement characters) displayed and comparison-eligible while omitting only the affected recognition's derived metadata or relationships. A file whose every row is a declaration row — a standalone hook file, an MCP carrier, a plugin catalog — is the exception, because its detail publishes declarations and never the file's bytes (FR-007): there a failure publishes the Diagnostic and the file's own facts, the reader reaches the text through the file opener (FR-022), and no surface holds a source for that file to be compared through.

The application MUST NOT inspect an unexpected failure's capacity, resource, or operational cause to reclassify, retry, or recover it; a failure not confined to one file fails the affected attempt, which commits no item, Source, recognition or derived result, scan-result body, success response, or generation. One closed cause check exists, at the single-file read boundary: the resource-exhaustion errno set — `EMFILE`, `ENFILE`, `ENOMEM` — identifies a condition of the machine rather than of the file being read, so such a failure routes to the attempt abort instead of becoming that file's per-file outcome (Constitution § Quality and Safety Standards). No other errno, message, or cause inspection exists. If work completes after its request loses publication authority through disable, shutdown, supersession, or failure, every late result MUST be discarded. Engine or operating-system termination is an environment limitation and MUST NOT be represented as a product guarantee.
- **FR-030**: Users MUST be able to rescan the active sources explicitly. Every admitted scan command MUST receive an opaque `scanRequestId`; every queued, active, complete, partial, or failed status MUST identify that request; and a successful generation MUST record the request that committed it. A prior status, snapshot, or generation MUST NOT satisfy completion of a newer request. Public `partial` MUST mean only the file-confined `partial` outcome in the Closed Scan Publication Outcomes table; no other incomplete state may be published. Repository and Global inspection keep independent generation sequences because their lifecycles are independent: the Repository sequence starts at bootstrap generation 0, while a Global sequence exists only from the enable commit that creates it until disable discards it. Scan results MUST be committed atomically as one generation snapshot of the owning sequence. A successful complete or partial commit MUST replace that sequence's previous snapshot and invalidate that sequence's previous-generation `FileDetail`, comparison selection or view, and editor-model state, which MUST NOT be restored from a stale response; a commit MUST NOT modify or invalidate the other sequence's state. A file's identity is its Source and Source-relative Path — stable across generations, so no per-generation file ID exists — and a detail request resolves that identity against the current committed snapshot: it serves the file the current generation holds at that path, or reports that it holds none, never a previous generation's record. If a rescan fails fatally before commit, the inspector MUST discard all of that scan's uncommitted results, including partial results, retain the last successfully committed snapshot, mark it as stale for that Source because the rescan failed, and show the failed request's error. An all-rejected Global attempt MUST produce no commit.

### Key Entities

- **Inspection Session**: The transient user activity containing exactly one Repository Source created during bootstrap without filesystem I/O from the selected Repository root defined by FR-001, zero to four member Global Sources, current scan results, comparison selection, and diagnostics.
- **Scan Request**: One admitted Repository initial scan or explicit rescan, or one nonempty initial-enable/retry `GlobalBatchScan`, identified by one opaque `scanRequestId`. A deterministic all-rejected Global initial attempt or retry is `active-no-job` and creates no Scan Request. A Global batch uses one request for all of its admitted tool roots rather than one request per Source. Every Scan Request's status and successful committed generation remain request-correlated so an older snapshot or status cannot satisfy a newer request.
- **Source**: An explicit source identity with a kind (`Repository` or `Global`), exactly one root location, enabled state, and scan status. The Repository Source exists at session bootstrap with a stable `sourceId` and an escaped root label. A Global Source is created only by its atomic post-consent commit and is additionally identified by exactly one member of the fixed four-member set — the three supported tools plus the shared agent home; customization files of different types within that root remain separate inventory items.
- **Source-relative Path**: A customization file's display, filtering, lookup, and selection path relative to the one root of its owning Source — the exact raw entry names joined with `/`. It is repository-relative to the selected Repository root only for the Repository Source; each Global Source uses its own root and namespace.
- **Customization File**: One discovered file within a Source, identified by its Source-relative Path, with its encoding — which also determines the derived read state — complete source text when readable, recognitions, relationships, and diagnostics.
- **Tool Recognition**: A tool-specific interpretation attached to a customization file, including tool, file type, the declared name, and its extraction outcome.
- **Evidence Assessment**: The atomic evidence state for one exact behavior, rule, or strategy subject — its closed documentation completeness and its ordered lifecycle qualifiers, kept separate and never reduced to one scalar or a qualifier union. It lives on the registry record it grades as a maintenance fact; no response, provenance, or relationship carries one, because the product reports what it found rather than how well a vendor documents its rules.
- **Relationship**: A non-executed reference from a customization file to another path or declared component, including boundary and resolution status without imported content expansion.
- **Diagnostic**: A session-only, actionable explanation of an empty result, deterministic malformed or binary content outcome, uncertainty, stale file, cycle, or boundary violation that does not duplicate customization source values. It has exactly one location scope. A file-scoped Diagnostic MUST require a coherent `sourceId` and `sourceRelativePath` pair: the file MUST belong to the identified Source, and the path MUST be that file's path within that Source. A source-scoped Diagnostic MUST require only `sourceId` and MUST forbid `sourceRelativePath`. There is no pathless scope: every Diagnostic MUST belong to a Source. This location scope is independent of whether the Diagnostic belongs to a committed generation or to the session lifecycle. An unexpected failure that is not confined to one file surfaces as an ordinary error and does not become a Diagnostic.

## Assumptions

- The initial release is a local, single-user inspection session; remote hosting, collaboration, accounts, and durable profiles are outside scope.
- All executable application code in the initial release is JavaScript/TypeScript: the browser runs generated client logic and declarative assets, and all non-browser product code runs on Node.js. Strict manifests, documentation, and license files remain non-executable package data. Per FR-038, users of the published package need no Rust toolchain, native compiler, native addon, platform-specific prebuilt binary, or package-lifecycle/runtime artifact download: the published package payload and the product runtime contain and require none of these. The one recorded closure exception is the `open` package's vendored POSIX-shell `xdg-open`, which the package's own selection policy uses on a Linux host whenever the vendored copy is executable, falling back to the system `xdg-open` otherwise (FR-038). Development-only tooling is outside the published package payload and outside this guarantee; contributor toolchains use separately pinned and audited third-party development dependencies that may include prebuilt platform-specific components or pinned certification-browser downloads, and none of these may enter the published payload or product runtime.
- Inspected Repository and opted-in Global roots are ordinary local paths controlled by the initiating user, in a workspace the user already trusts. Normal concurrent edits may surface as per-file diagnostics or a failed scan; the user rescans. The product does not defend against an adversarial local process, because a user who does not trust the workspace should not run the tool there.
- Product-issued source mutation is measured by mutation-capable filesystem requests and observable source properties, not by operating-system access-time policy. The Inspector never requests access-time changes; an OS-only read-side access-time update is recorded separately and does not establish a product mutation.
- The selected Repository root is the inspection boundary, not proof of the effective working directory used by any coding agent. Selecting a subdirectory through the invocation `cwd` or `--root` limits the Repository Source to that subtree; users rerun the command from the intended root or supply that root through `--root` to inspect a broader scope.
- Official customization formats can change. Their exact inspection paths, filenames, and extensions will be revalidated and frozen during planning, then published and covered by conformance fixtures. When a versioned release note directly adds behavior that a current general guide's exhaustive list omits, the specific addition remains in scope while the incompatible evidence is retained as `conflict`; unmentioned schema or ordering is not inferred.
- Official pages can be undated or rolling, and upstream features can be previewed, rolled back, or superseded. Evidence freshness is fixed by per-record `reviewedOn` dates and section fingerprints rather than page dates, and an undated or rolling page never establishes a version gate. A previewed feature keeps its closed `preview`/`experimental` lifecycle qualifiers; a rolled-back or superseded assertion is re-reviewed on drift and is removed or retained as `conflict` when directly contradicted. Neither state is presented as `stable` or resolved by inference.
- Global inspection covers the documented user-level customization files named by FR-015 through FR-017 and FR-045 — instructions, rules, skills, commands and prompts, agents, settings, hooks, MCP declarations, output styles, and the personal plugin marketplace, each below its consented member root. Documented user surfaces outside those roots or outside the product's closed kind set — VS Code profile files, LSP configuration, extensions, workflow scripts, and managed or remote configuration — require separate consent and future specification work.
- Source text, the displayed declared name, authored relationship targets, and comparison content are presented without credential masking so authored differences remain visible. Environment-variable references in inspected content remain literal and are not resolved; the product has no reveal workflow. The loopback-bound local host is the API access boundary and the whole boundary; no confirmation step stands in front of authored content and no notice stands beside it. The bundled browser holds the content in memory only and drops it on the client-data purge.
- The inspector may perform syntax-only parsing, reading the value a parser resolves for a declaration the recognized kind publishes, frozen-catalog classification, and projection of documented structural order, scope, condition, selection, and reference relationships. It does not interpret natural-language meaning, determine correctness, effectiveness, compliance, or quality, rank content, or advise remediation; a parse diagnostic is a descriptive failure, not a validation result.
- File, collection, parser, transport, queue, time, and concurrency capacity is inherited from Node.js, the parser, the operating system, the filesystem, the browser, and the execution environment. The Inspector defines no numeric capacity ceiling and never inspects a thrown or rejected operation to classify its cause or to classify customization content as valid or invalid.
- Public Node.js filesystem promises may not be force-cancellable. Disable, shutdown, or supersession revokes publication authority and discards late results. The product does not promise physical cancellation of kernel I/O or process survival after an uncaught startup error.
- Comparisons are limited to two distinct customization files at a time in the initial release and do not merge or edit content.
- Product documentation and the supported matrix will use official vendor documentation as the normative external dependency; undocumented behavior will remain explicitly uncertain.
